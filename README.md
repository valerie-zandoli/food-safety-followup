# Food Safety Follow-Up

[Watch the showcase film on YouTube](https://youtu.be/6t9ewV_8y48)

**Showcase film (1:31)**: a filth-flies violation cited twice in 15 days at one restaurant, followed from the public NYC inspection record to the manager's completed follow-up. Inspection records are from NYC Open Data; follow-up entries are illustrative. [Download the film](docs/media/food-safety-follow-up-showcase.mp4).

Food Safety Follow-Up is a course prototype for a food safety manager overseeing sweetgreen restaurants in New York City. It brings public restaurant-inspection findings and manager-entered follow-ups into one review workflow, helping the manager identify citations that need attention and keep corrective actions connected to their source records.

The homepage explains the workflow and shows permit-match coverage and the last successful city import. Choose **Open locations** to reach the map and matching location list at `/locations`. The manager opens a restaurant's inspection history grouped by year, reviews citations and repeated violation codes, compares supporting records, and records an action with an owner, due date, and notes. Completing a follow-up requires an explicit manager decision and a completion note; city inspection data alone cannot confirm that a correction occurred.

The project is based on the [sweetgreen Senior Food Safety Manager job description](https://careers.sweetgreen.com/jobs/8191701?gh_jid=8191701), which includes reviewing sanitation violations and driving documented corrective action in the NYC Region. This independent course project is not affiliated with sweetgreen and has no access to its internal systems or records. The scope and requirements are in [PRD.md](PRD.md); the app's data limits are described below.

## Run the app

Use Node.js 20.10 or newer. Run `npm install`, then `npm run dev`, and open `http://localhost:3000`. Run `npm test` and `npm run build` for the current checks.

The screens read the [backend API](#backend-api). In the default mode, build the location list from the saved city permit list and load city records using `npm run data:sync`, `npm run data:seed-matches`, then `npm run data:import`. These commands use the saved permit list (`data/permit-directory.json`), the confirmed matches (`data/confirmed-matches.json`), and NYC Open Data; nothing is read from Sweetgreen's website. Candidate permit matches for any location added later remain unverified until a manager confirms them. The screens show match coverage, source labels, and refresh dates. City records do not confirm corrective action.

For an offline demonstration, run `npm run dev:sample` instead. It serves the labeled fictional records from [`data/preview.json`](data/preview.json) through a separate API store in `.data-sample/`. The default city-data store is `.data/`; neither store is committed. Follow-up creation, edits, completion notes, and internal-check link decisions are saved on the server and survive browser refresh. `npm run seed:sample` resets the sample store, including its saved actions. An empty default store shows no locations until the import steps are run.

The frontend includes a homepage, location list/map, location detail, record comparison, follow-up create/edit, and completion-dialog screens. Pins and rows use the same location IDs. The API supplies flags and counts; findings retained as history remain visible without offering new actions. Missing inspection data is distinct from a no-violation inspection. Internal checks are unavailable unless fictional demo records have explicitly been seeded; the app has no company internal data.

## Backend API

The backend is a set of Next.js Route Handlers in `app/api` over a small server library in `lib/server`. It builds the NYC Sweetgreen list from the public locations page, verifies each location's NYC Open Data CAMIS permit by address, imports public inspection records, applies the flag rules, and saves manager follow-ups. The screens call these endpoints for records and saved actions. Their response shapes extend the sample contract in `data/preview.json`.

### Set up the live data

Use the saved permit list and confirmed matches already included in the repository: run `npm run data:sync` and `npm run data:seed-matches`, then `npm run data:import`; it imports verified locations only. `npm run data:match` and `npm run data:confirm -- <locationId> <camis>` remain for a location added later: review candidates with `npm run data:status` and confirm only candidates you have verified. Leave uncertain matches unverified. Fictional demo seeding is optional. The city service can be slow (one lookup took 45 seconds) and sometimes returns "service unavailable"; the client waits up to 90 seconds and retries, and a failed lookup leaves stored inspections and follow-ups intact.

| Command | What it does |
| --- | --- |
| `npm run data:permits` | Builds `data/permit-directory.json` from NYC Open Data alone: every permit whose name contains SWEETGREEN (41 on 2026-11-12; 38 are our locations, 3 are unclaimed). City fields only; one request. The Sweetgreen website scraper it replaced was deleted on 2026-11-12. |
| `npm run data:sync` | Builds the location list from `data/permit-directory.json` and `data/confirmed-matches.json` (stable ids; names such as "Sweetgreen, 125 Chambers St", addresses, phone, and map position come from the city record) and loads it into the store (`.data/`). Locations start as unverified. |
| `npm run data:seed-matches` | Restores the 38 confirmed location-to-permit matches into the store, so it reaches 38 verified locations without the manual steps. Run it after `data:sync`. |
| `npm run data:match` | Looks each location up in the city dataset by address. **Verified** needs the street address and a Sweetgreen business name to agree. Anything less becomes a **candidate** for the manager to decide, or stays unverified. A Sweetgreen-named permit within 250 m of the location's own map position, or with the same phone number, is also offered as a candidate, with its distance and the address the city lists. A permit in another borough is never offered, and a permit is never offered to two locations. Map coordinates come from the matched city record. |
| `npm run data:status` | Shows coverage, freshness, and each candidate with the reason it was not verified. |
| `npm run data:backup` | Copies the store to `.data/backups/` now. Every write also copies the version it replaces there and keeps the newest 20. Keep one copy off this computer; a backup in the same folder does not survive losing the disk. |
| `npm run data:restore -- <file>` | Puts a backup file back as the store, after backing up the store it replaces. With no file, lists the backups, newest first. It refuses a file that is not valid JSON or not a store. |
| `npm run data:confirm -- <locationId> <camis>` | The manager picks one candidate permit for a location. A confirmed match is never replaced by a later automatic one. |
| `npm run data:import` | Imports inspection records for verified locations. Re-importing yields the same records and ids, and a finding keeps its id when the city removes or reorders other findings with the same code, so a follow-up never moves to a different finding. If the city request fails, stored records and follow-ups stay as they were and the error is recorded. |
| `npm run seed:demo` | Adds two fictional checks to up to three verified locations that have city citations: one that names the code of the location's most recent citation (called a temperature or pest check when that citation's description says so, otherwise an audit) and a walkthrough with no citation. Both say they are fictional. |

To try the whole contract without city data, run `npm run dev:sample`. It creates the labeled sample store in `.data-sample/` when it is missing, never in the live store, and starts the app on it. `npm run seed:sample` rebuilds that store. The commands are written in Node, without Unix-only shell syntax, so they work in Windows shells too (a test guards this). `.env.example` lists the settings; none is required.

### Endpoints

All responses are JSON and are never cached. Dates are ISO (`2026-11-09`); times are ISO date-times.

| Request | Returns |
| --- | --- |
| `GET /api/locations` | `{ source, importStatus, locations[] }` for both the map pins and the list rows. Each location has `id`, `name`, `address`, `coordinates` (`[lat, lng]` or `null`), `coordinatesSource` (`NYC Open Data inspection record`, the city geocoder source named in the record, `Sample fixture`, or `null`), `camis`, `matchStatus` (`verified`, `candidate`, `unverified`), `dataState` (`records`, `no-records`, `not-imported`, `unmatched`), `citationCount` (`null` when there is no inspection record to count), `openFollowUpCount`, `overdueFollowUpCount`, `flagCount`, `candidateCount`, `lastRefreshed`, `sourceUrl`, `isSample`. |
| `GET /api/locations/:id` | `{ locationId, location, importStatus, inspections[], internalChecks[], followUps[], flags[], regionalSignals[] }`. Inspections are newest first, each with `outcome` (`citations`, `no-violations`, `not-yet-inspected`, `unknown`), `source`, `sourceUrl`, grade and score when present, and `citations[]`. Add `?regionalMonths=12` (a whole number from 1 to 120) to count only citations from the last 12 months toward `regionalSignals`; `regionalWindow` echoes the choice. Each internal check carries `source: "Fictional demo check"`, a `suggestedCitationId` only when it names an explicit code, and `link` (the manager's decision or `null`). |
| `POST /api/follow-ups` | Creates a follow-up from `{ locationId, citationId?, checkId?, owner, dueDate, notes, status?, completionNote? }`. Needs a citation, a demo check, or both. Returns the saved record with `201`. |
| `PATCH /api/follow-ups/:id` | Updates `owner`, `dueDate`, `notes`, `status` (`Open`, `In progress`, `Complete`), or `completionNote`. `Complete` requires a completion note. The linked finding cannot change. Returns the saved record. |
| `PUT /api/internal-checks/:id/link` | The manager sends `{ decision: "linked" \| "dismissed", citationId? }`. Linking uses the suggested citation unless one is given. Returns the saved check. |
| `POST /api/import` | Refreshes city records. Off unless `FSF_IMPORT_KEY` is set; send it as the `x-import-key` header. |
| `GET`, `POST`, `DELETE /api/session` | The shared access code. `GET` returns `{ protected, protectReads, signedIn }`. `POST { code }` signs a browser in with an HttpOnly, SameSite=Strict cookie that lasts seven days (`Secure` behind HTTPS); `DELETE` signs out. Five wrong codes from one address lock it out for a minute. See assumption 7. |
| `GET /api/health` | For an uptime monitor. `200` with `{ status: "ok", store: "readable", locations, verifiedLocations, lastSuccessfulImport, lastImportFailed, importStale }` when the store can be read; `503` with `{ status: "unavailable" }` when it cannot. Counts and times only, never records. A stale city import is reported in `importStale` but does not fail the check, because stored findings and follow-ups stay usable. |

`importStatus.state` is `ok`, `stale` (older than 72 hours), `failed` (the last attempt failed; `lastSuccess` and the stored records are still shown), `never-run`, or `not-connected` (sample store). `importStatus.warning` is a sentence when the last refresh kept stored records for a verified permit the city returned nothing for (a closed restaurant drops out of the city data, and the city can also fail to return rows), and `null` otherwise. An answer with no rows at all fails the refresh when a verified location already has current stored inspections; those records stay unchanged. If none has current stored inspections, an empty answer is a normal no-records result. Errors look like `{ "error": { "code", "message", "fields"? } }` with status 400 (bad JSON), 404 (unknown id), 413, 415 (not `application/json`), or 422 (field problems, one message per field). Imported city fields are read-only: no endpoint can change an inspection or citation.

Flags use the PRD's two types plus a separate regional list. `Needs review` is a citation with no linked follow-up (a completed follow-up still counts as linked). `Repeat code` is the same code on different inspection dates at one location and stays after an earlier follow-up closes. `regionalSignals` lists codes that appear at two or more covered locations and are never merged into a location's flags.

### Assumptions

Each gap in the PRD gets a logged assumption, with how to check it. Safe means small and easy to undo; risky means it touches what the manager reads or real data.

1. **Directory source.** Gap: the PRD names Sweetgreen's locations page as the source, and Sweetgreen's terms bar scraping it. Assumption: the location list comes from the city permit list instead. Each location keeps a stable id and its confirmed permit (`data/confirmed-matches.json`) and takes its name, address, phone, and map position from that permit's city record (`data/permit-directory.json`). Names read "Sweetgreen, <street address>", with the city's capitalization and spacing cleaned and its words kept. Why: city records only, so nothing depends on content that the terms forbid reading. Check: `npm run data:permits` rebuilds the permit list; `tests/directory.test.mjs` checks 38 unique ids, city-only fields, and a position for each. Safe. This replaced the Sweetgreen locations page snapshot, which was deleted on 2026-11-12.
2. **What is New York City.** Gap: the PRD says New York City only. Assumption: the permit list holds city permits only, and the five boroughs are still recognized by ZIP range when addresses are matched. Why: the city dataset covers only the city. Check: `tests/directory.test.mjs` requires a New York City ZIP code for every location. Safe.
3. **CAMIS verification.** Gap: the PRD says address, not name alone, but not how strict. Assumption: street, building number, ZIP code, and a Sweetgreen name must all agree to verify; any single mismatch is a candidate. Why: a wrong match would put another restaurant's violations under this location. Check: `npm run data:status` lists every candidate and the reason. Risky. Result on 2026-11-09, from `npm run data:status` at 17:50 UTC: 38 of 38 locations verified, 29 automatically and 9 confirmed by the manager, with 118 inspections and 271 citations imported at 17:39 UTC. Each automatic match is within 116 m of the location's own map position on sweetgreen.com (median 32 m). The 9 confirmed matches were checked against that position, the page's phone number, or the city's geocoder (see assumption 13). Earlier totals quoted elsewhere (29 of 38, then 31 of 38) were earlier steps of this same run. The Brooklyn permit at 1153 Broadway was not offered for NoMad because the borough differs.
4. **Who confirms a candidate.** Gap: the PRD says the manager confirms uncertain matches during setup, with no screen for it. Assumption: a command-line step, `data:confirm`. Check: ask whether the manager needs a screen. Safe.
5. **Map coordinates.** Gap: the PRD takes pins from the matched city record, and one city record has none (Penn Plaza). Assumption: use the city record's coordinates when they fall inside New York City; otherwise use the position from the NYC Planning Labs geocoder (a city service), recorded with its source in `data/confirmed-matches.json` for that one location, and name the source in `coordinatesSource`. Why: a source-labeled fallback keeps the location visible when city coordinates are missing. Check: a location with no position anywhere still appears in the list. Safe.
6. **Where records are kept.** Gap: the PRD asks for a persistent store without naming one. Assumption: one JSON file in `.data/`, written under a lock so a request and an import cannot overwrite each other. Why: nothing to install, works on Node 20.10, one manager. Check: replace `lib/server/store.js` with SQLite or Postgres before more than one person uses it; a file does not persist on serverless hosting. Risky for deployment, safe locally. This is limited to the local, single-host demo; serverless or multiple-instance deployment needs durable storage.
7. **One shared access code, no accounts.** Gap: the PRD allows only the manager and excludes accounts. Assumption: locally the API is open, so run it on your own computer or a private network; for a public copy, set `FSF_ACCESS_CODE` (at least 12 random characters). Every change (save a follow-up, link records, complete an action) then needs the code, entered once on the Manager access page (`/access`) or sent by a script in the `x-access-code` header or as a bearer token; the import keeps its own key and the health check stays open. Reading stays public unless `FSF_PROTECT_READS=1`, which suits a private copy. A code shorter than 12 characters blocks every change instead of protecting weakly; changing the code signs everyone out. The code is shared, not personal, so it proves "someone who knows the code", not who; anyone who knows it can change records, and sharing it with a second person is a policy choice, not a technical limit. Check: `tests/accessCode.test.mjs` (wrong, missing, tampered, and expired codes; lockout; cookie flags; short codes; protected reads). Risky if the code is weak, reused, or posted somewhere public. Without any code, the app still sends security headers on every response (a content security policy that allows only this site and OpenStreetMap map tiles, no framing, no content sniffing, a strict referrer policy, and no camera, microphone, or location access); they are set in `next.config.mjs` and checked by `tests/securityHeaders.test.mjs`. Strict-Transport-Security is left to the host, because it only applies over HTTPS.
8. **Reopening a completed follow-up.** Gap: the PRD requires a manager action and note to complete, and is silent on undoing it. Assumption: allowed; the completion note and time clear and the history keeps every change. Safe.
9. **Stale data.** Gap: no freshness limit is given. Assumption: 72 hours (`FSF_STALE_AFTER_HOURS`). Safe.
10. **Regional signals.** Gap: no time window is given. Assumption: all history, any two covered locations. Check: with real data this may be noisy; consider a date window. Safe. The optional `?regionalMonths=12` parameter limits the signals to the last 12 months.
11. **Newest first.** Gap: the sample data lists inspections oldest first. Assumption: the API returns newest first, which suits real history. Check: the screens must not assume the sample order. Safe.
12. **Demo checks on real locations.** Gap: the PRD wants fictional checks for the same locations. Assumption: add only notes that say they are fictional and claim nothing about the restaurant. Check: every card and export shows the `Fictional demo check` source. Safe.
13. **Map position and phone as evidence.** Gap: the PRD says to verify by address, but the city sometimes lists a corner or alternate address for the same storefront (66 East 55th Street for "60 E 55th St"). Assumption: a Sweetgreen-named permit within 250 m of a location's listed position, or with the same phone number, is offered as a candidate. It is never verified automatically. The 9 matches that were not automatic were confirmed from 2026-11-09 to 2026-11-11 using the positions and phone numbers that Sweetgreen's pages then published, the NYC Planning Labs geocoder, and a map check; those decisions now live in `data/confirmed-matches.json`, and the location list no longer reads Sweetgreen's pages (its listed position and phone now come from the city record). Why: on 2026-11-09 all 29 automatic matches were within 116 m of the page's position (median 32 m). Check: `npm run data:status` shows each distance. Two permits can share one corporate phone number, so a phone match is evidence, not proof. Safe as a candidate; risky if it verified on its own.
14. **Dates are New York dates.** Gap: the PRD gives due dates with no time zone, and a server or browser can run in any zone. Assumption: every calendar date is a New York date, wherever the code runs. A follow-up is overdue when its due date is before today's New York date, and the regional window counts back from that date. Why: a server set to UTC would call a follow-up due today overdue from 19:00 in New York, and the screens and the API could disagree. Check: `tests/newYorkDates.test.mjs` runs the rule under five host time zones and across both daylight-saving changes. Safe; a manager outside New York would need a different zone.

### What the data cannot show

The inspection results come from NYC Open Data (DOHMH New York City Restaurant Inspection Results). What follows was checked on 2026-11-09 against the city's data dictionary, Health Code Article 81, and Chapter 23 of Title 24 of the Rules of the City of New York, plus counts from the stored data and the city's live data.

- **A correction never shows.** A restaurant can "cure" a first-time violation by sending proof within 7 days. The violation stays on the record and no score or grade changes, so the data cannot show that anything was corrected. A completion note stores the manager's account of corrective work; the prototype does not independently verify it. Of the 271 stored citations, up to 99 carry codes that can be cured (10F, 10B, 09C, 08B, 20-08); which were cured is unknown.
- **"Repeat code" is this project's rule.** It means the same violation code on different inspection dates at one location. The city's own repeat penalties apply only to certain unscored violations (plastic straws and tobacco, for example), not to food-safety codes, so the flag is a prompt to look, not a legal finding.
- **Counts are not weighted by severity.** The city scores each violation at a condition level from I to V (for example by the number of flies), but the dataset gives only the code and a critical flag. When several pest types are cited in one inspection, the city scores only the highest. A count of citations says nothing about how serious each one was.
- **Critical is not the same as a public health hazard.** The dataset's critical flag covers both. Codes 04N, 04L, and 04M are critical but are not public health hazards.
- **Some codes are not scored.** Codes 15 to 22 are administrative or special-program violations (calorie posting, plastic straws, and the healthy-eating poster, for example). They do not count toward a score or a grade. They are 17 of the 271 stored citations.
- **10F is a broad upkeep code.** Since the rules adopted in 2021 (proposed in 2020), "conditions conducive to pests" with no pests present are cited as 10F, along with dirty or damaged floors, walls, and equipment. It is 64 of 271 citations and appears at 35 of 38 locations, so it says little about any one restaurant.
- **The city removes records.** Violations dismissed at a hearing are removed from the dataset, and restaurants that close drop out of it. Counts can fall between refreshes. The dataset keeps about three years of inspections for each restaurant.
- **Almost every inspection finds something.** All 118 stored inspections have at least one violation. That is typical: in the 12 months before 2026-11-09 only 0.3 percent of New York cycle initial inspections found none, and none of the 41 Sweetgreen-named permits or 98 salad restaurants had one. The pace matches too: the median is two cycle initial inspections per restaurant in three years, here and citywide.
- **Rules change over time.** Code meanings and thresholds changed with the rules adopted in 2021 (proposed in 2020), the cure rule started on 6 March 2023, and new unscored codes arrived in 2025. The stored data (October 2022 on) uses the current table, but a count across years mixes rule periods. Each row keeps the city's own description of its violation.

### How well the match rule works

Measured on 2026-11-09 by running the rule fresh on all 38 locations against every Sweetgreen-named permit in the city data (41 permits):

- The rule alone verified 29 locations, and all 29 agree with the final match (29 of 29). A person was needed for 9 of 38.
- The other 9 were offered as candidates with the correct permit ranked first every time, and no wrong permit was offered to any location. A person confirmed all 9.
- The measure is partly circular, because the manager confirmed those 9 using the same kinds of evidence (distance and phone). An independent address check (the NYC Planning Labs geocoder on the page address, compared with the building in the city record) agrees on the building for 33 of the 37 locations it could test. Two more are supported by a corner address (61st + Lex) or an exact phone number (Penn Plaza). Two had page and permit addresses in different buildings by that geocoder, so they were checked on a map on 2026-11-09 and both agree: at Hudson Yards (the page says 10 Hudson Yards, the permit says 501 West 30th Street) OpenStreetMap shows one Sweetgreen within 900 m, 24 m from the page pin and 62 m from the permit pin; at NoMad (the page says 1153 Broadway, the permit says 1164 Broadway) both the city permit and OpenStreetMap place the store at 1164 Broadway, 73 m from the page pin. Both permits have an inspection in the last 2 years (2026-04-21 and 2025-09-22). The page address at NoMad looks off by a few doors, across the street.
- The correct permit is within 227 m of the page position for every location that can be measured (median 32 m). A 100 m radius would contain it for 35 of 38 locations and a 250 m radius for 37 of 38; at 250 m two wrong permits sit inside some radius, and none was offered to a location.
- A phone number on the page equals the permit's phone for only 8 locations, because the city's phone is whatever the owner supplied and some permits share one number. Phone is weak evidence.
- The three bullets above describe a one-time measurement on 2026-11-09 that used the positions and phone numbers on Sweetgreen's pages. Those pages are no longer read.

### Data sources and terms

- NYC Open Data is read through its public API. The city's data FAQ states no restrictions on use. The dataset's separate terms page no longer exists (checked 2026-11-09), and the general NYC.gov terms disclaim accuracy.
- Sweetgreen's public location pages were read once on 2026-11-09 for names, addresses, map positions, and phone numbers. Sweetgreen's terms of use (updated 25 July 2025) bar automated scraping (section 8(e)) and limit use to personal, non-commercial purposes (section 7.1). This is not legal advice. On 2026-11-12 the scraper and that snapshot were deleted: the location list now comes from NYC Open Data alone (`npm run data:permits`), the confirmed matches are kept in `data/confirmed-matches.json`, and names are the city's street addresses, not Sweetgreen's labels. Git history still holds the old files.

### Checks

`npm test` covers the store, the permit-based location list, address matching, the NYC client and import, the flag rules, and every endpoint. The tests use fake city responses, and a guard makes any request to the NYC Open Data service or sweetgreen.com fail, so a test run gives the same answer with or without a network. `npm run build` checks the route handlers.

A GitHub Actions workflow (`.github/workflows/ci.yml`) runs `npm ci`, `npm test`, and `npm run build` on Node 20.10 and the current long-term-support release for every pull request and every push to `main`, plus an `npm audit` that only reports. It is not a required check, so nothing in it blocks a merge. By choice it never runs the live city lookups (the `data:*` and `seed:*` commands stay manual), and it has no linting, browser tests, or deployment. Add those after the showcase if the team wants them.

## Free read-only snapshot

A copy of the app that needs no server and no payment: every screen reads plain files, and saving is turned off with a clear message.  It suits a public demo (for example for buyers) on any free static host.

- `npm run data:sync`, `npm run data:seed-matches`, `npm run data:import`, then `npm run build:snapshot` build it.  `data:seed-matches` restores the 38 confirmed location-to-permit matches from `data/confirmed-matches.json`, so a fresh store reaches the same 38 verified locations without the manual steps; `build:snapshot` writes `public/snapshot/` and a static export to `out/`.
- Set `NEXT_PUBLIC_BASE_PATH=/repo-name` when the site lives under a GitHub Pages address, and `NEXT_PUBLIC_REPO_URL` for the link in the banner.
- `.github/workflows/snapshot.yml` rebuilds it from live city data every Monday and publishes it to GitHub Pages; `.github/workflows/monitor.yml` checks it every day and fails (GitHub emails the owner) if the page is down or the data is more than 10 days old.  Both run only where the repository variable `SNAPSHOT_PAGES` is `true`.  Public repositories get Actions and Pages for free.
- Limits: it shows public city records and fictional demo checks only; nothing a visitor types is saved; the data is as old as the last Monday run.
